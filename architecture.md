# Architecture: Quarkus + browser-side hono/html HDA demo

## Overview

A **Hypermedia-Driven Application (HDA)**: the browser swaps in HTML fragments with htmx — no SPA,
no virtual DOM. The twist in this variant: the HTML fragments are **rendered in the browser**, not
on the server.

- **Quarkus 3.32.4** (plain **JDK 21**) — JAX-RS resources (`quarkus-rest` + `quarkus-rest-jsonb`),
  CDI (`quarkus-arc`), JDBC persistence. No GraalVM, no polyglot, no native image.
- **hono/html** — TypeScript components written with hono's `html` tagged-template function, bundled
  by esbuild into a single browser script `hx-hono.js`.
- **htmx 4 + hyperscript** — browser-side partial updates, plus a small custom htmx extension
  (`hono`) that runs the templates.

The backend is now a **plain JSON API**: every `/uiroute/*` endpoint returns the view model it used
to hand to the server-side renderer, wrapped in a `{ route, vm }` envelope. The `hono` htmx
extension intercepts that response, runs the matching hono template on `vm` in the browser, and
hands the resulting HTML string back to htmx for the normal swap.

The templates are plain functions — `(vm: SomeModel): HtmlResult => html`…`` — not JSX. `String(...)`
on the result yields the HTML. There is no `hono/jsx`, no `renderToString`, no virtual DOM anywhere.

*(This repo is the browser-rendering fork of `2026-03-15_hda-quarkus-graalvm-jsx-demo`, which runs
the same templates server-side inside a GraalVM `Context` pool. Everything below the transport
boundary — the codegen, the view models, the htmx/hyperscript choreography, persistence — is
unchanged between the two.)*

## Request pipeline

```
Browser  GET /
  → META-INF/resources/index.html                  [static shell, served by Quarkus/Vert.x]
      <div id="app" hx-get="/uiroute/Page" hx-trigger="load" hx-target="#app" hx-swap="innerHTML">
  → htmx fires the load-triggered request ↓

Browser  GET /uiroute/Page          [Accept: application/json — set by the `hono` extension]
  → PersonUIResource.uiroute("Page")
      → JTSPersonRouteName.valueOf("Page")          [unknown name → 404 NotFoundException]
      → PeopleService.personTableModel()            [SQL → Java record]
      → new PersonPageModel(tableModel)             [assemble view model]
      → return new UiResponse("Page", vm)           [JAX-RS + jsonb → application/json]

  ← {"route":"Page","vm":{…}}
  → `hono` extension, htmx_after_request hook:
        content-type is application/json → { route, vm } = JSON.parse(ctx.text)
        ctx.text = render(route, vm)                 [render.ts → personRoutes["Page"].render(vm)
                                                     → String(html`… Page(vm) …`)  — runs in the browser]
  → htmx swaps ctx.text into #app (innerHTML)        ← unchanged from here on
```

**The Java↔browser contract is the `{ route, vm }` JSON envelope.** The route name travels with the
data so the extension needs no extra header and no per-element attribute — the URL stays the only
place routes are named (`UiResponse` in `inbound/web`).

`PersonTable` is the one route that needs a `search` param instead of `id`, so it has its own
`@GET @Path("/PersonTable")` method rather than growing `uiroute()`'s signature; JAX-RS matches the
literal path before the `/{name}` template. The `uiroute()` switch's `default` branch throws
`IllegalStateException` for any route that has such a dedicated endpoint.

## The `hono` htmx extension — `inbound/web/hx-hono.ts`

`hx-hono.ts` is the single esbuild entry. It imports the local `render` function and registers one
htmx 4 extension:

```ts
import { render } from "./render";
declare const htmx: any;

htmx.registerExtension("hono", {
  // htmx 4 hard-codes `Accept: text/html`; the /uiroute/* endpoints only produce the
  // JSON envelope, so ask for JSON (HTML kept as a q=0.9 fallback for error pages / redirects).
  htmx_config_request: (_elt, detail) => {
    detail.ctx.request.headers["Accept"] = "application/json, text/html;q=0.9";
  },

  // htmx 4's sanctioned place to rewrite the response body before the swap
  // (this is htmx 2's transformResponse).
  htmx_after_request: (_elt, detail) => {
    const ctx = detail.ctx;
    const ct = ctx.response?.headers?.get?.("content-type") ?? "";
    if (!ct.includes("application/json")) return;   // mutations, errors → leave alone
    if (!ctx.text) return;
    const { route, vm } = JSON.parse(ctx.text);
    ctx.text = render(route, vm);                    // hono html`…` runs here
  },
});
```

Notes:

- **htmx 4 extension API** (not htmx 2): `htmx.registerExtension()`, underscored hook names
  (`htmx_after_request` = the `htmx:after:request` event), mutate `detail.ctx.text`. No
  `defineExtension` / `onEvent` / `transformResponse`.
- Extensions in htmx 4 are **global** — every registered hook runs for every request regardless of
  `hx-ext`. `index.html` still carries `hx-ext="hono"` for documentation/intent.
- **Load order**: `hx-hono.js` must load *after* `htmx.js` and must not be deferred past it — it
  calls `htmx.registerExtension` at parse time.
- Mutation responses (`PUT /person/{id}`, `DELETE /delete`) carry no body and no
  `application/json` content-type, so the hook no-ops on them — the header-driven
  `HX-Trigger` / `HX-Redirect` choreography is untouched.
- All components are synchronous (no async children), so `render()` returns a string synchronously.

### `render.ts`

```ts
export function render(route: string, vm: unknown): string {
  const defs = personRoutes as Record<string, RouteDefinition>;
  const def = defs[route];
  return String(def ? def.render(vm) : html`<div>ROUTE '${route}' NOT FOUND</div>`);
}
```

It does **not** dispatch itself — it looks `route` up in `routes.ts`'s `personRoutes` map. `String(...)`
at this boundary collapses `HtmlResult` (a boxed `HtmlEscapedString`, possibly a `Promise`) to the
primitive `string` the extension hands to htmx, and runs hono's stringify phase. `HtmlResult`
everywhere inside the components; stringify exactly once here (see `render.ts`'s header comment).

## First paint — the static shell

`GET /` serves a hand-written `src/main/resources/META-INF/resources/index.html` (Quarkus/Vert.x
serves it as the welcome file — there is no `RootResource`). It carries what the old server-side
`layout.ts` used to emit: `<html x-data="$store.darkMode">`, the `<head>` (bulma, htmx 4,
hyperscript, `main.js`, `dev.js`, alpine, Material Icons) plus `<script src="/js/hono/hx-hono.js">`
right after `htmx.js`, and the hero `<section>` with the dark-mode toggle. Its `#app` div does:

```html
<div id="app" hx-get="/uiroute/Page" hx-trigger="load"
     hx-target="#app" hx-swap="innerHTML"></div>
```

so the same extension renders the `Page` route client-side on load. `#app` is empty until that fetch
resolves (a brief first-paint flash — acceptable for the demo; a server-inlined bootstrap would be a
follow-up). `personpage.ts`'s `Page()` returns just the `.container` markup — no `Layout` wrapper.

## TypeScript layer — `inbound/web/*.ts`

esbuild bundles everything reachable from `hx-hono.ts` into one browser script:

```
esbuild src/main/java/dev/svenehrke/demo/inbound/web/hx-hono.ts \
  --bundle --platform=browser --format=iife \
  --outfile=src/main/resources/META-INF/resources/js/hono/hx-hono.js
```

`hono/html` is pure string work — no node deps — so it bundles cleanly for the browser. `htmx` is a
runtime global (htmx.js loads first); the extension references it via `declare const htmx: any`.

## Bundle shape — questions considered, and why it's left as one file

Two design questions come up as soon as you see the single `hx-hono.js`. Both were considered and
deliberately **not** acted on; recorded here so they don't get re-litigated.

### 1. `hx-hono.js` contains every template — should it be split and loaded on demand?

**Decision: no, not for now — measure first, and if it ever matters, split by *route*, not by
component.**

- The templates are `html`…`` tagged strings — no framework, no JSX runtime, no vDOM. A component is
  ~0.5–3 KB of source; the only shared runtime is `hono/html` (~1.5 KB gzipped). Minified + brotli'd,
  the whole current bundle is a few KB, and you have runway into the thousands of lines before size
  is a real concern. Step one is always: `esbuild --minify`, serve it compressed with a hashed name +
  long cache TTL, and look at the actual transfer size.
- One file is also an advantage here: one cache entry, one round trip, no fetch waterfall — a swap
  that composes several sub-components renders synchronously.
- **If it does get big:** the split unit should be the **route**, not the component (per-component
  splitting causes a fetch waterfall mid-render). There is already a canonical route list
  (`JTSPersonRouteName` / `personRoutes`), so a `route → () => import("./chunks/x.js")` map can be
  generated from that same source of truth.
- **The htmx catch that drives the design:** htmx 4 dispatches extension hooks *synchronously*
  (`#triggerExtensions` calls `fn(elt, detail)` and checks `=== false`, never awaits), so
  `htmx_after_request` **cannot** `await import(...)`. But htmx *does* `await ctx.fetch(...)`. So the
  clean integration point for lazy rendering is a `ctx.fetch` override in `htmx_config_request`:
  fetch the JSON, `await import()` the route's chunk, render, and return a synthetic
  `new Response(htmlString, { headers: { "content-type": "text/html" } })`. That also lets you drop
  the `htmx_after_request` hook entirely.
- Cheaper middle grounds: a few coarse feature bundles instead of per-route chunks; preload a route's
  chunk on `mouseenter`/`focus` of its `hx-get` element (like `hx-preload`); ship the shell routes
  (`Page`, `PersonTable`) in the initial bundle and lazy-load the rest.

### 2. `esbuild --bundle` inlines the `hono/html` runtime — should it be a separate file?

**Decision: no. Bundling it in is the path of least resistance and least breakage.**

- Nothing was hand-copied — `--bundle` inlines every import at build time; the `hono/html` runtime
  (the `html` tag, escaping, the `HtmlEscapedString` stringify phase) is pulled in next to the
  templates. `hx-hono.js` is a git-ignored build artifact; the source of truth is `package.json`
  (`hono@^4.13.5`), regenerated by `npm run build`.
- Splitting it out removes no bytes — it moves ~1.5 KB gzipped and adds an HTTP request. The
  "stable vendor chunk stays cached while app code changes" argument barely applies at 1.5 KB, and
  the shared-chunk benefit only pays off across *multiple* independently-loaded bundles (there is
  one).
- This is unlike htmx (loaded as its own `<script>`): htmx ships a ready-to-drop-in browser build,
  is ~50 KB, and is genuinely shared/stable. `hono/html` has no equivalent standalone browser build
  and is tiny.
- If it ever becomes worthwhile: a second esbuild entry `hono-runtime.ts`
  (`import * as h from "hono/html"; (window as any).__hono = h;`) loaded as a plain `<script>` before
  `hx-hono.js`, plus `--external:hono/html` and a one-line shim re-exporting `window.__hono` on the
  main build.

## Java → TS generation (Java is the source of truth) — unchanged

Two `process-classes`-phase Maven plugins keep the TS side in sync; both outputs are git-ignored and
rebuilt on every `mvn package` (`mvn compile` stops one phase too early).

1. **`cz.habarta.typescript-generator`** — scans `*Model` / `*VM` classes and the enums
   `JTSPersonRouteName`, `JTSPersonEventName`, and writes `generated/types/vm-types.d.ts`
   (`mapEnum: asUnion`, `outputFileType: declarationFile`). Types only, no runtime values.
2. **`org.codehaus.gmavenplus` inline Groovy script** (in `pom.xml`) — reflects over
   `HonoWebApiSharedConsts.HonoWebApiConsts` and writes `generated/types/web-api-consts.ts` with the
   two mutation path templates as **runtime** `const` strings (needed because `routes.ts` does
   `HonoWebApiConsts.PERSON.replace('{id}', id)`).

So: add a route → add the `JTSPersonRouteName` enum value, add its `case` in `PersonUIResource`, add
the `personRoutes` entry in `routes.ts` (the `satisfies` makes a missing entry a TS error).

The Java view-model records are still the single source of truth for the VM shapes — they are now
serialized by jsonb straight onto the HTTP response instead of being handed to a JS engine, but the
shapes the browser sees are the same.

## htmx / hyperscript choreography — unchanged

- `hx-get` / `hx-put` / `hx-delete` on elements → partial swaps.
- Hyperscript `_="…"` attributes → client-side DOM events, no JS files.
- `<template hx-trigger="…">` — invisible htmx triggers embedded in rows, listening for custom events.

Event names come from `JTSPersonEventName` (`PERSON_UPDATED`, `PersonDetailsRow_CloseCmd`,
`PersonEditor_CloseRequested` — the last two `// TS-only`). `.ts` code never writes an event name as
a bare string; it calls `eventName('…')`, which typechecks against the generated union. Names use
`UPPER_SNAKE` / `Word_Word` — both safe to `send` unquoted in hyperscript (a hyphenated name is not).

**Saving an edit:**
1. Save button fires `PUT /person/{id}` with `hx-swap="none"`.
2. `PersonActionResource` sets `HX-Trigger: {"PERSON_UPDATED": {"id": 5}}` (empty body — the `hono`
   extension no-ops on it).
3. htmx dispatches a `PERSON_UPDATED` DOM event `{id: 5}`.
4. A `<template hx-trigger="PERSON_UPDATED[detail.id === 5] …">` inside the row re-fetches the row,
   which comes back as another `{ route, vm }` envelope and is rendered client-side.

**Bulk delete** fires `DELETE /delete`; `PersonActionResource` responds with `HX-Redirect: /` (the
static shell, *not* `/uiroute/Page` — that would dump JSON in the address bar). The shell reloads and
its `#app` re-fetches `Page`.

`HTMXConsts.java` holds the response-header name constants.

## Dev browser live-reload (`quarkus.profile=dev`)

1. **`watch.ts`** (Bun) watches `src/main/java/**/*.ts` → runs esbuild → rewrites
   `src/main/resources/META-INF/resources/js/hono/hx-hono.js`.
2. **`JsBundleWatcher`** (`@IfBuildProfile("dev")`, `@Scheduled(every = "1s")`) polls that file's
   `lastModified`; on change → `DevReloadSSE.broadcastReload()`. There is no server-side JS engine
   to re-initialise anymore — a changed bundle just means "tell the page to reload".
3. **`DevReloadSSE`** (`@IfBuildProfile("dev")`, Vert.x `@Route("/dev-reload")`) pushes a `reload`
   event; `META-INF/resources/js/dev.js` listens with `new EventSource("/dev-reload")` and calls
   `location.reload()`.

Note: browsers HTTP-cache `hx-hono.js` aggressively — the SSE reload picks up a rebuilt bundle, but
a manual refresh may need a hard reload (Ctrl+Shift+R).

## Key design decisions

| Decision | Rationale |
|---|---|
| hono `html` tagged templates (not JSX), run **in the browser** | Plain functions, no JSX toolchain; the same code that ran server-side in the GraalVM fork now runs client-side unchanged |
| `{ route, vm }` JSON envelope as the Java↔browser contract | Route name travels with the data — no extra header, no per-element attribute; the URL stays the only place routes are named |
| One esbuild entry (`hx-hono.ts`) bundling the extension + `render` | No global, no separate "render bundle" + "extension" split |
| Static `index.html` for first paint, no SSR | Nothing renders HTML on the server; `#app` bootstraps itself with `hx-trigger="load"` |
| Java as the source of truth, TS generated | Route names, event names and VM shapes can't drift; a rename on the Java side is a TS compile error |
| `.ts` co-located with the Java web layer | Templates are the web tier, not a separate project |
| Plain JDK 21, no GraalVM / polyglot / native image | The rendering moved to the browser — the JVM only needs to serve JSON and static files |
